# Fix `tls_client_auth` Client Metadata for OIDCC Config Tests

## Overview

OIDCC configuration test variants using `client_auth_type=tls_client_auth` fail in `INTERRUPTED` state because the plan config sent to the conformance suite lacks the required `tls_client_auth_san_dns` metadata field. The suite's `ValidateClientCertificateForTlsClientAuth` validator requires exactly one of the `tls_client_auth_*` binding fields to be set on the client object. This plan adds the missing field so the affected modules progress past interruption.

## Current State Analysis

### Root Cause

The harness builds plan configs in two functions:

1. `buildPlanConfig` (`conformance/harness/execute.go:812-906`) — used for plan-based test creation
2. `buildStandaloneModuleConfig` (`conformance/harness/execute.go:909-944`) — used for standalone module creation

Both functions set `client.certificate` (the PEM) when `client_auth_type` is `tls_client_auth` or `self_signed_tls_client_auth`, but neither sets any `tls_client_auth_*` metadata binding field.

### What the suite expects

When the suite processes a `tls_client_auth` variant:

1. `AbstractOIDCCClientTest.setupTlsClientAuth()` (`conformance/.upstream/.../AbstractOIDCCClientTest.java:1330-1335`) configures `validateClientAuthenticationSteps = OIDCCValidateClientAuthenticationWithTlsClientAuth`.
2. `OIDCCValidateClientAuthenticationWithTlsClientAuth` (`conformance/.upstream/.../OIDCCValidateClientAuthenticationWithTlsClientAuth.java:13-18`) calls `ValidateClientCertificateForTlsClientAuth`.
3. `ValidateClientCertificateForTlsClientAuth` (`conformance/.upstream/.../ValidateClientCertificateForTlsClientAuth.java:29-61`) counts how many of `tls_client_auth_subject_dn`, `tls_client_auth_san_dns`, `tls_client_auth_san_uri`, `tls_client_auth_san_ip`, `tls_client_auth_san_email` are present on the `client` object. It requires exactly **one** to be set.
4. Currently, the client object has **zero** of these fields, so `fieldCount != 1` and the test interrupts with the error from line 57-60.

### Certificate details

The mTLS certificate is generated by `cmd/genfapikeys/main.go:103-144`:

- **Subject DN**: `CN=client-mtls.localhost,O=Lanyard Conformance`
- **SAN DNS**: `client-mtls.localhost`
- No URI, IP, or email SANs

### Scope of fix

This only affects `tls_client_auth` variants. The `self_signed_tls_client_auth` variant does NOT require `tls_client_auth_*` metadata fields — its `@VariantConfigurationFields` annotation only requires `jwks`/`jwks_uri` (`AbstractOIDCCClientTest.java:194-197`), and it uses a different validation sequence.

## Desired End State

The `tls_client_auth` OIDCC config plan variants include `tls_client_auth_san_dns: "client-mtls.localhost"` in the client config payload. The suite validates this against the presented certificate's DNS SAN and passes validation. The three affected modules (`oidcc-client-test-idtoken-sig-none`, `oidcc-client-test-signing-key-rotation-just-before-signing`, `oidcc-client-test-signing-key-rotation`) and all other `tls_client_auth` variants progress past the `ValidateClientCertificateForTlsClientAuth` check.

### Key Discoveries

- The `@VariantConfigurationFields` for `tls_client_auth` (`AbstractOIDCCClientTest.java:187-192`) declares `client.tls_client_auth_subject_dn`, `client.tls_client_auth_san_dns`, `client.tls_client_auth_san_uri`, `client.tls_client_auth_san_ip`, `client.tls_client_auth_san_email` as configuration fields — these are optional; the suite accepts any one of them.
- The certificate already has `DNSNames: []string{"client-mtls.localhost"}` (`cmd/genfapikeys/main.go:125`), so `tls_client_auth_san_dns` is the natural match.
- The `certificate` field (PEM) is separate from the `tls_client_auth_*` metadata fields. The PEM is used by the suite to present the cert during the test; the metadata field tells the suite how to bind the cert to the client.

## What We're NOT Doing

- Not modifying the upstream conformance suite code
- Not changing the certificate generation (`cmd/genfapikeys/main.go`)
- Not changing `self_signed_tls_client_auth` handling (that has its own bug: `bug_oidcc_config_self_signed_tls_client_auth_invalid_cert`)
- Not adding `tls_client_auth_subject_dn` (we chose SAN DNS binding)
- Not changing FAPI2 plan config (FAPI2 uses `mtls` auth type, not `tls_client_auth`)

## Implementation Approach

Add `tls_client_auth_san_dns: "client-mtls.localhost"` to the plan config in both config builder functions when `client_auth_type == "tls_client_auth"`. This is a minimal, targeted fix that directly addresses the suite's validation requirement.

## Phase 1: Add `tls_client_auth_san_dns` to Plan Config

### Overview

Add the missing `tls_client_auth_san_dns` metadata field to client config payloads when the auth type is `tls_client_auth`.

### Changes Required

#### 1. `buildPlanConfig` — Add metadata for plan-based configs
**File**: `conformance/harness/execute.go`
**Lines**: 879-884

After the existing `certificate` field assignment, add `tls_client_auth_san_dns` to both `client` and `client2`:

```go
if authType == "tls_client_auth" || authType == "self_signed_tls_client_auth" {
    if certPEM, _, err := loadClientMTLSCert(); err == nil {
        cfg["client"].(map[string]any)["certificate"] = certPEM
        cfg["client2"].(map[string]any)["certificate"] = certPEM
    }
    if authType == "tls_client_auth" {
        cfg["client"].(map[string]any)["tls_client_auth_san_dns"] = "client-mtls.localhost"
        cfg["client2"].(map[string]any)["tls_client_auth_san_dns"] = "client-mtls.localhost"
    }
}
```

#### 2. `buildStandaloneModuleConfig` — Add metadata for standalone module configs
**File**: `conformance/harness/execute.go`
**Lines**: 926-930

After the existing `certificate` field assignment, add `tls_client_auth_san_dns`:

```go
if authType == "tls_client_auth" || authType == "self_signed_tls_client_auth" {
    if certPEM, _, err := loadClientMTLSCert(); err == nil {
        client["certificate"] = certPEM
    }
    if authType == "tls_client_auth" {
        client["tls_client_auth_san_dns"] = "client-mtls.localhost"
    }
}
```
