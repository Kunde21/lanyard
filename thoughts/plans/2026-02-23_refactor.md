# Refactor Plan (2026-02-23)

## Goals / Non-Goals

- Keep exported APIs stable (`oidc`, `jwks`, `rp`); refactor should be behavior-preserving.
- Reduce duplication (HTTP fetch + TTL, discovery refresh logic, conformance harness parsing + timing/failure boilerplate).
- Improve readability and testability by introducing small, reusable internal helpers.
- Non-goal: redesign semantics (timeouts, cache policy, error types) unless explicitly called out.

## High-Level Sequence (Lowest Risk First)

1. Extract shared helper(s) without changing call sites (pure moves).
2. Replace duplicated call-site logic to use helpers (mechanical refactors).
3. Consolidate twin flows (`refreshProvider`/`refreshAuthorizationServer`) behind one internal template.
4. Tackle dynamic JSON parsing in conformance harness last (highest behavioral risk).

## 2) Unify “GET JSON with ETag + preview-on-error” Flow

### Targets

- `oidc/http_fetch.go` (`fetchRawJSON`)
- `jwks/http_fetch.go` (`fetchJWKS`)
- Shared constants: `maxErrorBodyBytes` is duplicated.

### Plan

- Introduce `internal/httputil/fetchjson.go` with a focused helper.
- Keep error typing behavior:
  - `oidc` returns `*HTTPStatusError` for non-200.
  - `jwks` wraps errors in `*FetchError`.
  - The helper should return enough info (status code + body preview) for package-specific wrapping.

### Helper responsibilities

- Build request, set `Accept: application/json`, set `If-None-Match`.
- Execute request via provided `*http.Client`.
- Compute `(freshUntil, fetchedAt, etag)` consistently.
- Handle `304` by returning `notModified=true` without decoding.
- On non-200 (and not 304), read a limited preview body.
- On 200, decode JSON into `out` (or call a decoder callback).

### Verification

- `go test ./...`
- Explicitly run:
  - `go test ./oidc -run Test`
  - `go test ./jwks -run Test`

## 3) De-duplicate Discovery Refresh Logic

### Targets

- `oidc/discovery.go` (`refreshProvider`)
- `oidc/discovery.go` (`refreshAuthorizationServer`)

### Plan

- Keep public entry points unchanged:
  - `DiscoverProvider`
  - `DiscoverAuthorizationServer`
- Introduce a single internal refresh template in `oidc/discovery_refresh.go` that handles:
  - `singleflight` via `c.discoveryGroup.Do(cacheKey, ...)`
  - ETag extraction from `existing`
  - 304 update behavior (refresh freshness, keep metadata)
  - Cache set + type assertion checks
  - “serve stale cache” debug log behavior

### Shape

- Use a struct of callbacks (avoid generics unless already used in repo):
  - `wellKnownURL(issuer) (string, error)`
  - `fetch(ctx, url, etag) (... + metadata, error)`
  - `validate(expectedIssuer, metadata) error`
  - `newEntry(metadata, etag, freshUntil, fetchedAt) *CacheEntry`
  - Kind check: provider vs AS

### Verification

- `go test ./...`
- Run unit tests that cover discovery behavior.
- Run at least one integration test suite locally if it’s stable in your environment.

## 7) Conformance Harness: Make Suite API Parsing Less Dynamic

### Targets

- `internal/conformanceharness/suiteclient.go` parsing functions:
  - `parseAvailablePlans`, `parseModules`, `parseVariants`, `parseStringField`
- `internal/conformanceharness/suiteclient.go` (`doJSON`)

### Plan (Incremental)

1. Update `doJSON` to decode into `json.RawMessage` rather than `any`.
2. Introduce typed DTOs for the shapes we use:
   - Available plans list
   - Created plan
   - Test info
3. Implement one string-field fallback helper based on `json.RawMessage`:
   - `firstString(m map[string]json.RawMessage, keys ...string) string`
4. Replace `any` casting with deterministic JSON unmarshal paths.
5. Keep `RawConfig` only if needed; consider storing as `json.RawMessage` to avoid lossy conversions.

### Benefits

- Fewer silent `continue`s on type mismatch.
- Less runtime `any` assertion logic.
- Easier, more deterministic unit tests (feed sample JSON -> compare typed output).

### Verification

- Add/extend tests in `internal/conformanceharness/*_test.go` covering:
  - Modules being `[]string` vs `[]object`
  - Variants map shapes
  - Mixed key names (`planName` vs `name`, etc.)
